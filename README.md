# ATM API

ASP.NET Core API банкомата: создание счёта, пользовательские и административные сессии, баланс и история операций. Данные хранятся в памяти процесса.

## Возможности

- Административная сессия по системному паролю и создание счёта.
- Пользовательская сессия по номеру счёта и PIN-коду.
- Пополнение, снятие, получение баланса и истории для счёта текущей сессии.
- Авторизация по GUID-ключу сессии.
- Валидация HTTP-моделей и ответы 400/401 для предусмотренных ошибок.
- Swagger UI, подключённый в приложении.

## Логика работы

Система разделяет административные действия и операции владельца счёта. Администратор создаёт счета, а пользователь работает со своим счётом через отдельную сессию.

1. **Вход администратора.** Клиент передаёт системный пароль. При совпадении с настройкой приложения создаётся административная сессия, а клиент получает её GUID-ключ.
2. **Создание счёта.** Администратор передаёт ключ своей сессии и PIN-код нового счёта. Система присваивает счёту номер, устанавливает нулевой баланс и добавляет запись о создании в историю.
3. **Вход пользователя.** Клиент передаёт номер счёта и PIN-код. После проверки создаётся пользовательская сессия, связанная с этим счётом. В ответ возвращается новый GUID-ключ.
4. **Операции со счётом.** Для просмотра баланса, пополнения, снятия и истории клиент передаёт ключ пользовательской сессии. Счёт определяется по сессии: указывать его номер в каждом запросе не требуется. Административная сессия не заменяет пользовательскую для этих операций.

Пополнение увеличивает баланс на переданную сумму. При снятии доменная модель `Account` сначала проверяет достаточность средств: если денег не хватает, баланс остаётся прежним, а API возвращает ошибку. При успешном пополнении или снятии клиент получает обновлённый баланс.

История хранится отдельно для каждого счёта. Создание счёта, успешное пополнение, успешное снятие и просмотр баланса добавляют запись с типом операции, временем UTC и балансом на этот момент. Неудачная попытка снятия и запрос самой истории новых записей не создают. История показывает остаток после операции, а не отдельное поле с суммой изменения.

Например, после создания счёта баланс равен 0. Пополнение на 1000 увеличивает его до 1000, снятие 250 оставляет 750. Последующий запрос баланса возвращает 750 и также записывается в историю. Попытка снять ещё 1000 завершится ошибкой и не изменит остаток.

Счета, сессии и история доступны между HTTP-запросами в пределах одного запуска приложения. После остановки процесса эти данные теряются.

## Архитектура

Приложение построено по принципам луковой архитектуры (Onion Architecture). В центре находится доменная модель, вокруг неё — прикладные сервисы и их контракты, снаружи — HTTP-представление и инфраструктура хранения данных.

| Слой | Состав |
|---|---|
| Domain | `Account`, `Money`, операции и сессии |
| Application.Contracts | Контракты сервисов, запросы, ответы и DTO |
| Application.Abstractions | Порты репозиториев, запросы выборки и `IPersistenceContext` |
| Application | `AccountService`, `SessionService`, `OperationHistoryService` |
| Infrastructure | In-memory реализации репозиториев |
| Presentation.Http | ASP.NET Core controllers и HTTP-модели |
| Lab5 | Composition root: настройка и запуск приложения |

Зависимости направлены к внутренним слоям: `Domain` не зависит от других проектов решения, `Application` использует доменную модель и абстракции репозиториев, а `Infrastructure` реализует эти абстракции. HTTP-контроллеры зависят от `Application.Contracts`. Прикладные сервисы не зависят от HTTP-представления и конкретного способа хранения данных.

Проект `Lab5` связывает реализации через Microsoft.Extensions.DependencyInjection (MSDI). Каждый модуль предоставляет методы расширения для регистрации своих зависимостей. Репозитории зарегистрированы как singleton, контекст — scoped.

## Сборка и тестирование

Нужен .NET SDK 9.0.306 или более новый patch в той же feature band, допускаемый `global.json`. При первом восстановлении необходим доступ к NuGet. Команды выполняются из корня репозитория.

```sh
dotnet restore atm-api.slnx
dotnet build atm-api.slnx -c Release --no-restore
dotnet test atm-api.slnx -c Release --no-build
```

GitHub Actions повторяет эти команды для `main` и pull requests. Рабочие процессы подготовлены локально; запуск на GitHub не выполнялся.

## Запуск и пример

Для локальной демонстрации задайте системный пароль через окружение. Исходное значение удалено из конфигурации и всей подготовленной истории. Ниже — новое открытое демонстрационное значение, не секрет. Формат пароля в текущем API — GUID. Переменную необходимо задать до запуска: существующий код не проверяет её обязательность и иначе использует значение GUID по умолчанию.

```sh
export AdminSession__SystemPassword=11111111-2222-4333-8444-555555555555
dotnet run --project src/Lab5/Lab5.csproj -c Release --no-build --no-launch-profile -- --urls http://127.0.0.1:5085
```

Swagger UI доступен по адресу `http://127.0.0.1:5085/swagger`. Для завершения — Ctrl+C.

Откройте [examples/requests.http](examples/requests.http) в HTTP-клиенте Rider или совместимом редакторе. Выполните запросы сверху вниз, подставляя GUID сессий и номер созданного счёта в переменные в начале файла. После пополнения на 1000 и снятия 250 баланс составит 750. История покажет создание счёта и последующие операции, включая чтение баланса.

| Метод и маршрут | Вход |
|---|---|
| `POST /api/session/create-admin` | `systemPassword` в query |
| `POST /api/account/create` | `sessionKey`, `pinCode` в JSON |
| `POST /api/session/create-user` | `accountId`, `pinCode` в JSON |
| `POST /api/account/put-money` | `sessionKey`, `money` в JSON |
| `POST /api/account/withdraw` | `sessionKey`, `money` в JSON |
| `GET /api/account/get-balance` | `sessionKey` в query |
| `GET /api/operation/get-history` | `sessionKey` в query |

Ключи сессий возвращаются JSON-строками, номер счёта и баланс — JSON-числами. История — массив объектов `time`, `balance`, `operationType`. Неверная авторизация возвращает 401, недостаток средств и ошибки валидации модели — 400. Суммы HTTP-запросов и PIN принимаются как положительные целые числа.

## Ограничения

Данные и сессии исчезают после перезапуска. Репозитории используют обычные коллекции в памяти без синхронизации; корректность конкурентных операций не гарантируется. PIN хранится в модели напрямую, срока жизни сессий нет. Системный пароль передаётся в query, поэтому может попасть в журналы запросов. Это локальная демонстрация архитектуры, не готовый банковский сервис.

Существующие тесты проверяют пополнение и снятие с моками репозиториев; они не являются интеграционными HTTP-тестами. Запросы в примере образуют отдельный ручной сценарий.
